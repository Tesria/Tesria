# Writing the docs

How the Docs space (dev-plan 10.5, 15.6; called Support until 2026-09-24,
which is why this folder and its scripts keep that name) is written. The pages are
generated by `scripts/docs/publish-docs.sh` from the section modules in
`sections/`, and exported to tesria.com/docs as the product's official
documentation. These rules came from reviewing the first version (2026-09-23),
which read as very basic and dry; the pilot pages that follow
them were approved: *Trusting the local certificate*, *Opening Tesria by
name*, *Panels*, *Creating a space* and *Templates*. They live in the
sections they belong to (`installation.mjs`, `editor-elements-1.mjs`,
`manual-spaces.mjs`) and are the models to copy.

## Who it is for, and how it sounds

- **Someone new**, to wikis and to running software. Never assume they know
  what a certificate, a keystore, Docker or a permission model is. Explain
  what a thing is and **why they would want it**, with a real example, then
  how.
- **US English, and no em dashes anywhere** (use a period, colon, comma or
  parentheses). Curly apostrophes (’) as the existing pages do.
- **Warm and plain.** Short sentences. Second person ("you"). Name buttons
  exactly as the app does, in bold.
- **Only what exists.** Check every claim against the code
  (`src/web/src`, `src/Api`). If you cannot confirm something, leave it out.
  Never describe a planned feature.
- **Placeholders**: `your-server` stands for the reader's own address, with
  a note the first time it appears on a page.

## Structure

- **A page starts with what the thing is and why it matters**, in a
  paragraph or two, before any steps.
- **Procedures are numbered steps**: `h(3, 'Step 1: …')`, what to do, and a
  picture of where to click when it helps. If the steps mirror an app screen
  that numbers its own steps, use the same numbers and titles.
- **Lists, not tables, for anything longer than a few words.** A table of
  explanations runs off a phone. Tables are for short entries: a command and
  what it gives, a setting and its values.
- **Panels** sparingly: `info` for context, `note` for something easy to
  miss, `success` (shown as Tip) for a better way, `warning`, `error`. Start
  each with a few bold words that say what it is about.
- **Link to other docs pages** with `pageLink('Exact title')` (or
  `pageLink('Title', 'link text')`), never a bold name alone.
- **Say how to get there, every time** (2026-09-24: pages named
  a screen and assumed the reader knew where it was). Never "in
  Administration, Users" alone: use `...adminAt('Users')`, which adds where
  Admin is on a computer, a narrow window and a phone, or
  `...profileAt('Sessions')` for a card on the profile. A page about one
  screen starts with how to open it.

### Element pages (User manual → The editor → Elements, and Live content)

Every element page has the same shape, so readers know where to look:

1. **What it is and when to use it**: one or two paragraphs.
2. **Insert it**, always the first heading: a short table of the slash
   command(s) (`/info` → An Info panel) and a sentence on the **+** toolbar
   menu, and what happens with text selected.
3. **Every variant, live on the page, each with when to use it and an
   example.** The real element, built with the lib helpers, not a picture of
   it: every chart type (bar, column, line, pie), every panel type, each list
   style, table options, status colors, and so on. The chart page was
   flagged in review for showing none of its types.
4. **Changing and removing it**: what the menu or settings above it do.
5. **Good practice**: a few bullets.
6. **Related elements**, linked.

A picture only where the element cannot be shown live or where using it is
the point, and then preferably an **animation** (a short recording of doing
it). The Panels page is the model (`sections/editor-elements-1.mjs`).

## Pictures

The docs rules: **a picture only where it shows something words cannot**
(where a control is, what a layout looks like), **never a picture of text the
page already says**, **one per row, never side by side**, **every picture
with a shadow**, **the right size on every device**, and boxes and arrows on
the thing to click.

- Use `picture(pageId, shotName, alt, caption)` for a desktop picture,
  `phonePicture(...)` only in an **On a phone** section where the phone is
  genuinely different, and `animation(pageId, shotName, caption)` for a
  recording. **Never** the old `figure()` or `phoneFigure()`: they put
  pictures side by side.
- **Take close-ups in a narrow window**: `viewport: NARROW` (480 × 900) and
  `phone: false`. At about the width it is shown, its text is near the size
  of the page's on a desktop and still readable on a phone. A crop of a
  1280px window came out at a quarter of its size on an iPhone.
- **Crop to what matters** with `clipTo` (a selector, or a list whose union
  is taken) and `clipPad`. If the padding would show half of something
  unrelated, hide it with a `css` step (`visibility: hidden`).
- **Mark the control**: `annotate: [{ type: 'box', target: selector, pad: 5 }]`,
  `{ type: 'arrow', target, from: 'below' | 'above' | 'left' | 'right', label }`,
  `{ type: 'note', target, label, dx, dy }`. Targets are CSS selectors (no
  `:has-text`); to target a button by its text, tag it first with an `eval`
  step that sets a `data-shot` attribute.
- **Animations**: a shot with `record: { size: { width: 480, height: 400 } }`
  and the same `viewport`, `waitFor`, `lead`, `tail`, and steps with
  `typeSlowly`, `moveTo`, `click`, `wait`. Record at 1x (the recorder does
  not scale 2x). A recording that opens `/spaces/DEMO/new` makes a draft;
  the harness discards it.
- **Stills that open a new page** leave a draft unless a following shot
  closes it: `{ name: '<shot>-closed', skipCapture: true, phone: false,
  steps: [{ click: '.page-actionbar button:has-text("Close")' }, { wait: 1200 }] }`.
- **Only the Tesria Demo space and the fictional accounts** (Alex Rivera,
  Sam Okafor, Priya Natarajan, Mei Chen, Jordan Brooks) may appear. Admin
  screens list real accounts on a real instance: filter tables to the
  example accounts with an `eval` step, as `administration.mjs` does, and
  hide anything else personal. Pages in Demo are found by title with
  `demo('Title')`.
- Steps run **before** the shot's settle wait, so start with `{ wait: 2500 }`.

## A section module

```js
export const shots = ({ demo }) => [ /* harness shots */ ]
export async function prepare({ lib, author, demo, demoId }) { /* optional: data the pictures need; return {} */ }
export async function build(helpers) { /* write the pages */ }
export async function cleanup({ author }) { /* optional: move pages, remove retired attachments */ }
```

`build` receives the lib's document builders (`doc`, `p`, `h`, `text`,
`bold`, `italic`, `code`, `ul`, `ol`, `li`, `panel`, `table`, `codeBlock`,
`status`, `date`, `math`, `chart`, `live`, `layout`, `expand`, `decision`,
`tasks`, `task`, `quote`, `hr`, `toc`, `excerpt`, `smartLink`, `embed`,
`image`, `gallery`, `fileBlock`, `pageProperties`, …), the site helpers
(`page(title, parentId, doc)` writes a page only if it differs, `ensure`,
`attach`, `attachCurrent`, `tree`, `space`), `top` (the top-level pages by
title), and `picture`, `phonePicture`, `animation`, `pageLink`.

**Keep every existing page title**, so pages are rewritten in place. A new
page is fine; a page that should go is listed in the module's header comment
for the owner to confirm. Check syntax with `node --check`.
